# 통합 DB 스키마 설계안 (FlatMap + SafetyRoad)

> 상태: **설계안(초안)**. 코드·DB·`_legacy/`는 수정하지 않았다.
> 근거: `_legacy/db-dumps/` 두 덤프(2026-11-07 생성, pg_dump 18.3)와 두 백엔드의 엔티티·리포지토리·서비스 코드.
> 표기: 확인하지 못한 항목은 **확인 불가**로 적었다. "추정"은 데이터 패턴에서 추론한 것이라 검증이 필요하다.
> 설정 파일(`application.properties/yml`)은 키 이름만 확인했고 값은 읽거나 옮기지 않았다.

## 2. 통합안 — 시설 테이블

### 2.1 `safety_facility` 하나로 합치기

FlatMap의 `cctv_locations`, `security_lights`를 SafetyRoad의 `safety_facility` 구조로 흡수한다.

```sql
CREATE TABLE safety_facility (
    id            bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    facility_type varchar(30)  NOT NULL,           -- CCTV / SECURITY_LIGHT / POLICE_STATION ...
    name          varchar(255),
    address       varchar(255),
    region_code   varchar(10),                     -- FlatMap security_lights에서 가져옴 (nullable)
    geom          geometry(Point, 4326) NOT NULL,
    data_source   varchar(80)  NOT NULL,
    created_at    timestamp(6) NOT NULL DEFAULT now(),
    updated_at    timestamp(6) NOT NULL DEFAULT now(),
    CONSTRAINT chk_facility_type CHECK (facility_type IN ('CCTV','SECURITY_LIGHT','POLICE'))
);
```

결정 사항:

1. **컬럼명은 `geom`** 으로 정한다(SafetyRoad는 `location`). `location`은 의미가 모호하고 DB 예약어와 겹칠 수 있다. 이식할 SQL은 리네임이 필요하다.
2. **`name`/`address` 길이는 255로 넓힌다.** 합치면서 잘리는 데이터가 없게 한다(SafetyRoad 100/200은 FlatMap보다 짧다).
3. **`region_code`를 추가**한다. FlatMap의 필터(`findByRegionCodeStartingWith`)가 쓰고 있다. SafetyRoad 쪽 행은 NULL로 두거나 좌표→행정구역 변환으로 채울 수 있다(**확인 불가**: 변환 원천 데이터를 확인하지 못했다).
4. **`data_source`는 NOT NULL**로 한다. 합칠 때 FlatMap 행에는 `FLATMAP_LEGACY`(가칭) 같은 값을 채우고, 원천을 알면 정정한다.
5. **`POLICE`는 정의를 정리**한다. 소방서가 섞여 있다. 선택지는 (a) `POLICE`를 그대로 두고 이름만 정리, (b) `POLICE`/`FIRE_STATION`으로 분리. 점수 가중(×5)이 걸려 있어 **(b) 분리 후 가중치를 설정으로 빼는 쪽을 권장**한다. 단 35건뿐이라 우선순위는 낮다.
6. **중복 방지**: `UNIQUE (facility_type, geom)`은 지오메트리 비교가 느리므로, 좌표를 반올림한 해시 컬럼이나 `UNIQUE (facility_type, data_source, ST_AsEWKB(geom))` 같은 인덱스를 쓴다. 이식 시 한 번 정제하고(아래) 이후 적재 코드가 `ON CONFLICT DO NOTHING`을 쓰게 한다.

### 2.2 이식 시 정제 규칙

| 단계 | 규칙 | 근거 |
|------|------|------|
| 1 | 깨진 행(`name`, `address`가 모두 `?`)은 **이식하지 않는다.** 단, 정상 출처에 같은 좌표가 없는 깨진 행(1,580건, CCTV·조명 구성 비율은 확인 불가)은 좌표만 쓸 수 있으나 이름 없는 시설이 된다. 정책 결정이 필요하다(§8 미결정 사항). | F1 |
| 2 | 같은 (종류, 좌표) 중복은 정상 출처 우선으로 1건만 남긴다. | F2 |
| 3 | FlatMap `cctv_locations` 중 SafetyRoad에 같은 좌표(약 5m 이내)가 있는 2,885건은 흡수 시 중복 처리한다. 나머지 69건은 FlatMap 고유다. | §1.1 |
| 4 | FlatMap `security_lights` 100건은 **버린다.** 성남 밖 데이터다. | F4 |
| 5 | 적재 후 `ST_Contains(성남 경계, geom)` 같은 범위 검증을 한다(**확인 불가**: 성남 경계 폴리곤 원천 없음). 대안으로 성남 격자 bbox(경도 127.04~127.18, 위도 37.33~37.52)를 임시로 쓴다. | §1.1 |

정제 후 예상 규모(참고): SafetyRoad 고유 키 16,631에서 깨진 행 처리 정책에 따라 줄어든다. **정확한 최종 건수는 확인 불가**(정책 결정 전).

### 2.3 FlatMap 전용 테이블 — 그대로 둘까, geometry로 바꿀까

**권장: geometry(Point,4326)로 전환하되, 당분간 `latitude`/`longitude`는 생성 컬럼(generated column)으로 유지한다.** 테이블은 그대로 따로 둔다(시설 하나로 합치지 않는다).

| 대상 | 권장 | 이유 |
|------|------|------|
| `accident_zones` | geom 전환, 별도 테이블 유지 | 시설이 아니라 위험 지점이다. 속성(type)과 의미가 다르다. |
| `protected_zones` | geom 전환, 별도 테이블 유지 | 반경이 의미 있는 구역이다(향후 폴리곤 가능성). |
| `welfare_facilities` | geom 전환, 별도 테이블 유지 | `phone`, `type` 등 전용 속성이 있다. |
| `shade_shelters` | geom 전환, 별도 테이블 유지 | 전용 속성은 적지만 "안전시설"이 아니라 쾌적성 레이어다. |
| `senior_centers` | geom 전환, 별도 테이블 유지 | `phone` 등 전용 속성. |

이유:

1. CLAUDE.md 규칙 3·4: 공간 데이터는 PostGIS + `JdbcTemplate`이고, 거리·반경은 `ST_DWithin`으로 한다. `latitude`/`longitude` 두 컬럼은 공간 인덱스를 쓸 수 없다. 현재 `SteepSlopeService`, `DetourService`는 `findAll()` 후 `haversineMeters` 루프를 돈다(규칙 4가 금지하는 방식).
2. 모두 행 수가 적다(39~406). 전환 비용이 작고 얻는 것(인덱스, 일관된 쿼리)이 크다.
3. 합치지 않는 이유: 속성이 다르고(phone, type), 프론트가 레이어별 엔드포인트를 따로 호출한다(`MapPage.js`). 하나로 합치면 `facility_type` 분기와 NULL 컬럼이 늘어난다. 대신 "안전시설"만 `safety_facility`로 묶는다.
4. **생성 컬럼으로 lat/lng를 남기는 이유**: 프론트·DTO가 `latitude`/`longitude`를 쓰고 있어 한 번에 바꾸면 이식 단위가 커진다(CLAUDE.md 규칙 5: 한 번에 하나씩). 생성 컬럼은 `geom`과 값이 어긋날 수 없다.

```sql
ALTER TABLE accident_zones
  ADD COLUMN geom geometry(Point,4326);
UPDATE accident_zones SET geom = ST_SetSRID(ST_MakePoint(longitude, latitude), 4326);
ALTER TABLE accident_zones ALTER COLUMN geom SET NOT NULL;
-- 이후 단계: latitude/longitude를 geom에서 파생되는 생성 컬럼으로 교체하거나 제거
```

> `ST_Y`/`ST_X`가 IMMUTABLE이라 `GENERATED ALWAYS AS (ST_Y(geom)) STORED`가 가능한지는 **로컬 DB에서 확인하지 않았다(확인 불가)**. 안 되면 뷰나 앱 계산으로 대체한다.
> 좌표가 NULL인 행이 있는지는 위 6개 테이블 중 `cctv_locations`, `security_lights`, `shade_shelters`만 확인했고 모두 0건이다. 나머지는 **확인 불가**다. `NOT NULL`을 걸기 전에 검사한다.

```sql
UPDATE steep_slope_areas SET geom = ST_SetSRID(ST_MakePoint(longitude, latitude), 4326);
```

- **`latitude`/`longitude`는 1단계에서는 유지**한다(`DetourService`, `SteepSlopeService`, 프론트 `MapPage.js`가 응답에 쓴다). `geom`이 원천이 되고, lat/lng는 읽기 전용 호환 컬럼으로 둔다. 소비 코드를 `geom` 기반 `ST_DWithin`으로 옮기면 2단계에서 제거한다.
- 행이 88개라 이중 보관의 어긋남 위험은 작지만, 갱신 코드(`ElevationService`, `CsvImportService`)가 두 곳을 따로 쓰지 않도록 쓰기 경로를 `geom` 하나로 모은다.

### 3.3 의미 분리 — F5 처리 (CLAUDE.md 도메인 규칙)

88건은 "붕괴위험 지정지"만 모은 표본이다. 보행난이도 임계값(3.18°/4.76°)을 적용하면 안 된다.

| 컬럼 | 조치 |
|------|------|
| `risk_level` | **이식하지 않는다**(또는 `legacy_walk_risk_level`로 이름을 바꿔 비노출 보관). 보행 임계값으로 만든 값이라 붕괴위험과 무관하다. |
| `grade` | 값은 **각도(°)** 다. 다만 출처가 행마다 다를 수 있다(CSV 원본값 vs `ElevationService`가 DEM으로 덮어쓴 값). 구분 컬럼이 없어 **행별 출처는 확인 불가**다. `grade_deg`로 이름을 바꾸고, 의미를 "지점 경사(°), 참고용"으로 문서화한다. |
| 신규 `hazard_type` | `COLLAPSE_RISK_DESIGNATED` 고정값. 붕괴위험 경고 레이어용이다. |
| `/steep-slope/risk-stats` | 현재 3단계 보행 등급을 집계한다. 이식 시 재설계가 필요하다(별도 단계). |

보행난이도는 이 테이블이 아니라 **경로 위 DEM 경사**로 따로 계산한다(`backend/dem/`에 Copernicus DEM이 있다). 두 축을 같은 테이블·같은 컬럼에 섞지 않는다.

### 3.4 정제

- 좌표 중복 10그룹: 같은 지점의 중복 등록인지, 서로 다른 급경사지가 같은 대표 좌표를 쓰는지 **확인 불가**다. 이름·지번을 비교해 판단한다.
- 성남 격자 밖 6건: 성남시 동쪽 경계 근처일 가능성이 있다(**확인 불가**).

## 4. `danger_zone` (300m 그리드) 이식 시 변경점

### 4.1 현재 구조 (실측)

- 격자 크기: 경도 0.0034° × 위도 0.0027°. 위도 37.4° 기준 약 300m × 300m이다.
- 범위: 경도 127.04~127.183, 위도 37.33~37.522.
- 점수: `facility_count` → 점수 변환 공식이 코드(`calculateSafetyScore`)와 **3,484행 전부 일치**한다. `HIGH ≤ 30 < MEDIUM ≤ 60 < LOW`.
- 시설 수 = `countWithinBounds`(종류 무관 전체) + `POLICE×5`. `countWithinBounds`가 POLICE도 세므로 POLICE는 실제로 **6배** 반영된다. 의도한 가중인지는 코드만으로 **확인 불가**다.
- 주의: `ST_Within`이 `safety_facility` 전체를 매 격자마다 센다. 격자 약 3,000개 × 쿼리 2~3회이고 공간 인덱스가 없다.

### 4.2 변경점

| # | 현재 | 변경 | 이유 |
|---|------|------|------|
| 1 | 중복 행 (F3) | 이식 시 `DISTINCT`, 재계산 시 `TRUNCATE` 후 단일 트랜잭션 | 중복 방지 |
| 2 | `for (lat += GRID_LAT)` 부동소수점 누적 | 정수 인덱스 `(grid_i, grid_j)`로 격자를 만들고 `ST_MakeEnvelope`로 폴리곤 생성. 가능하면 `ST_SquareGrid` 사용 | 누적 오차로 경계가 흔들린다. 재계산 결과 재현성 확보 |
| 3 | 격자마다 쿼리 2~3회(N+1) | `safety_facility`를 격자와 `JOIN`해 한 번에 집계 (`GROUP BY grid`) | 성능. CLAUDE.md 규칙 4의 정신(DB에서 계산) |
| 4 | `safety_facility.location` 컬럼명 | `geom`으로 변경 | §2.1 |
| 5 | 점수 임계(30/60)·가중(POLICE×5)이 코드에 하드코딩 | 상수 한곳으로 모으고 `danger_zone`에 `score_version` 컬럼을 둔다 | 공식이 바뀌면 과거 값과 구분 |
| 6 | `count == 0`이면서 주변도 비어 있는 격자는 제외 | 유지하되 `facility_count = 0`을 "위험"이 아니라 "**시설 데이터 없음**"으로 표기 | 아래 7번 참고 |
| 7 | `safety_score`가 낮으면 `HIGH`(위험) | 의미를 "안전시설 밀도"로 명시. 이름은 `danger_zone` 대신 `safety_grid`도 검토 | 시설이 없다고 곧 위험은 아니다. 1,742 격자 중 656개(고유 기준 0건 시설 격자)가 점수 10, `HIGH`다. 데이터 부재와 위험이 섞인다. |
| 8 | 테이블 이름 `danger_zone` | 이식 시 유지(프론트 계약), 이름 변경은 별도 단계 | 한 번에 하나씩 |
| 9 | 좌표계 4326 + 도 단위 격자 | 유지. 면적 계산이 필요하면 `geography` 캐스트 | 300m는 도 단위로 약 0.0027° 근사이고 정확한 정사각형이 아니다 |

추가 컬럼 제안:

```sql
CREATE TABLE danger_zone (
    id             bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    grid_i         int NOT NULL,
    grid_j         int NOT NULL,
    grid_polygon   geometry(Polygon, 4326) NOT NULL,
    safety_score   numeric(5,2) NOT NULL,
    facility_count int NOT NULL DEFAULT 0,
    risk_level     varchar(10) NOT NULL,
    score_version  smallint NOT NULL DEFAULT 1,
    calculated_at  timestamp(6) NOT NULL DEFAULT now(),
    UNIQUE (grid_i, grid_j)
);
```

> 이식하는 `safety_facility`가 §2.2 정제를 거치면 `facility_count`가 달라진다. **덤프의 `danger_zone` 값을 그대로 가져오지 말고, 정제된 시설 데이터로 재계산**하는 것을 권장한다.

- 데이터 입수 엔드포인트(`/api/safety/fetch/*`, `/api/steep-slope/fetch/*`)는 프론트에서 호출하지 않으며 관리용으로 보인다. 프론트는 `/safety/security-lights`도 호출하지 않는다(조명 레이어가 현재 UI에 없음).

## 6. 공간 인덱스(GiST) 필요 목록

PostGIS 확장이 먼저 필요하다. 두 덤프 모두 공간 인덱스가 하나도 없다.

| 테이블 | 컬럼 | 용도 |
|--------|------|------|
| `safety_facility` | `geom` | 반경·경로 주변 시설 수(`ST_DWithin`), 격자 집계 |
| `safety_facility` | `facility_type` (btree 보조) | 종류 필터. 필요하면 `(facility_type, geom)` 복합은 GiST에서 `btree_gist` 필요 |
| `danger_zone` | `grid_polygon` | 지점이 속한 격자 조회(`ST_Intersects`) |
| `steep_slope_areas` | `geom` | 경로 주변 급경사지(`ST_DWithin`) |
| `accident_zones` | `geom` | 경로 주변 사고다발지 |
| `protected_zones` | `geom` | 보호구역 |
| `welfare_facilities` | `geom` | 시설 조회 |
| `shade_shelters` | `geom` | 시설 조회 |
| `senior_centers` | `geom` | 시설 조회 |

```sql
CREATE INDEX idx_safety_facility_geom      ON safety_facility   USING GIST (geom);
CREATE INDEX idx_danger_zone_polygon       ON danger_zone       USING GIST (grid_polygon);
CREATE INDEX idx_steep_slope_geom          ON steep_slope_areas USING GIST (geom);
-- accident_zones / protected_zones / welfare_facilities / shade_shelters / senior_centers 동일
CREATE INDEX idx_safety_facility_type      ON safety_facility (facility_type);
```

**미터 단위 반경(F6)**: 두 가지 중 하나를 고른다.

- (A) 쿼리에서 `geom::geography`로 캐스트하면 위 GiST를 쓰지 못한다. 이를 위해 표현식 인덱스 `USING GIST ((geom::geography))`를 추가한다. 시설 테이블에 권장한다.
- (B) 한국 TM 좌표계(예: EPSG:5186)로 저장하는 별도 컬럼을 둔다. 컬럼이 늘어나서 비권장이다.

(A)를 쓰면 SafetyRoad의 "도 단위 반경" 호출은 **미터 단위로 바꿔서** 이식해야 한다. 이식 단위 테스트(CLAUDE.md 규칙 5)로 반경 기준을 고정한다.

작은 테이블(39~406행)은 GiST 없이도 빠르지만, 규칙 4의 일관성과 후속 확장을 위해 같이 만든다. 이 판단의 성능 근거는 실측하지 않았다(**확인 불가**).

## 7. 마이그레이션 순서 제안 (Flyway)

### 7.1 사전 조건

- Flyway 의존성 추가. Spring Boot 3.2.0 BOM이 관리하는 버전은 9.x 계열로 **추정**하나 `mvn dependency:tree`를 실행하지 않아 **확인 불가**다. 버전에 따라 PostgreSQL 전용 모듈(`flyway-database-postgresql`)이 따로 필요할 수 있다.
- `spring.jpa.hibernate.ddl-auto=update`를 `validate`(또는 `none`)로 바꾼다. 현재 `update`라서 Flyway와 충돌한다.
- 비공간 테이블(`users`, `favorites`)은 JPA를 유지하므로 `validate` 시 컬럼이 일치해야 한다.
- 대상 DB가 PostGIS 확장을 설치할 수 있는지는 **확인 불가**다(로컬 DB를 보지 않았다).
- 운영·개발 DB에 이미 FlatMap 스키마가 있으면 `baseline`이 필요하다. 현재 DB 상태는 **확인 불가**다.

### 7.2 버전별 마이그레이션

| 버전 | 파일 | 내용 |
|------|------|------|
| `V1` | `V1__baseline_users_favorites.sql` | 기존 `users`, `favorites` 정의를 베이스라인으로 고정 (이미 있으면 `baselineOnVersion`) |
| `V2` | `V2__enable_postgis.sql` | `CREATE EXTENSION IF NOT EXISTS postgis` |
| `V3` | `V3__create_safety_facility.sql` | `safety_facility` 신규 생성 + GiST·타입 인덱스 |
| `V4` | `V4__create_danger_zone.sql` | `danger_zone` 신규 생성(격자 인덱스 포함) + GiST |
| `V5` | `V5__geom_flatmap_zone_tables.sql` | `accident_zones`, `protected_zones`, `welfare_facilities`, `shade_shelters`, `senior_centers`에 `geom` 추가·채움·GiST (**테이블마다 마이그레이션 분리 권장**: V5a~V5e) |
| `V6` | `V6__steep_slope_geom_and_semantics.sql` | `steep_slope_areas.geom` 추가, `hazard_type`, `risk_level` 처리(§3.3), GiST |
| `V7` | `V7__load_facilities.sql` | FlatMap `cctv_locations` 데이터 흡수 (데이터 마이그레이션 — 정제 규칙 적용). SafetyRoad 데이터는 SQL 마이그레이션이 아니라 **별도 적재 스크립트**로 하고, 이 파일은 구조만 담는 것을 권장 |
| `V8` | `V8__recompute_danger_zone.sql` | 정제된 시설 기준 재계산 (또는 앱 기동 후 서비스가 수행) |
| `V9` | `V9__drop_legacy.sql` | `cctv_locations`, `security_lights`, 사용 안 하는 `road_segments`, `routes`, `route_segments`, `accident_records` 삭제. **소비 코드를 모두 옮긴 뒤 별도 단계에서** 실행 |

원칙:

1. **구조(DDL)와 데이터를 분리**한다. 5MB급 SQL 덤프를 마이그레이션 파일에 넣지 않는다. 데이터는 별도 로더로 적재하고 건수를 검증한다.
2. **한 번에 하나씩**(CLAUDE.md 규칙 5): 각 버전은 대응하는 기능 이식과 단위 테스트가 통과한 뒤 완료로 본다.
3. 삭제(V9)는 가장 마지막에 둔다. 그 전까지 구 테이블과 신 테이블이 함께 있어 롤백이 쉽다.
4. 단계가 끝날 때마다 `docs/CHANGELOG.md`에 요약한다(규칙 7).

### 7.3 이식 순서(기능 기준)

1. 시설(`safety_facility`) + 반경·경로 주변 조회 → 가장 효과가 크다(SafetyRoad 핵심).
2. `danger_zone` 재계산·조회.
3. `steep_slope_areas` geom 전환 + 보행/붕괴 축 분리.
4. FlatMap 전용 5개 테이블 geom 전환.
5. 구 테이블·미사용 테이블 정리.

## 8. 미결정 사항 / 확인 불가 목록

### 결정이 필요한 것 (사용자 판단)

1. 깨진 이름(`?`)을 가진 시설을 **좌표만이라도 이식할지**, 아예 버리고 재수집할지. (F1)
2. `POLICE` 35건에 소방서가 섞인 문제를 분리할지. (§2.1-5)
3. `risk_level`을 폐기할지, 비노출 보관할지. (§3.3)
4. `danger_zone`을 이름 그대로 둘지 `safety_grid` 등으로 바꿀지. (§4.2-7)

### 확인 불가

- 깨진 한글의 원문 복원 가능 여부(원본 CSV와 대조하지 않았다).
- `data_source = ???????`가 `경기데이터드림`이라는 점은 코드와 글자 수에서 **추정**한 것이다.
- FlatMap `cctv_locations`의 원천(출처 컬럼 없음).
- `favorites.user_id` FK 유무.
- `accident_zones`, `protected_zones`, `welfare_facilities`, `senior_centers`의 좌표 NULL 여부.
- `steep_slope_areas`의 `grade` 값이 행마다 CSV 원본인지 DEM 계산값인지.
- `steep_slope_areas` 좌표 중복 10그룹과 성남 격자 밖 6건의 성격.
- 대상 DB의 PostGIS 설치 가능 여부와 Flyway 버전.
- 생성 컬럼(`ST_Y`)이 실제 PostgreSQL에서 허용되는지.
- 프론트의 동적 URL 호출(문자열 검색에 잡히지 않는 경우).
- 성남시 경계 폴리곤 원천 데이터.
- 실제 쿼리 성능(어떤 인덱스도 벤치마크하지 않았다).

### 분석 방법 메모

- 행 수·분포는 두 덤프의 `COPY` 블록을 직접 파싱해 센 값이다. 덤프가 "현재 DB"와 같은지는 **확인 불가**다(덤프 생성 시점의 스냅샷이다).
- SafetyRoad 지오메트리는 EWKB 16진 문자열을 디코딩해 격자 크기·좌표 범위를 계산했다. 데이터베이스에 접속하지 않았다.
